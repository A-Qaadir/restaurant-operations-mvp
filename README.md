# ServiceOS working demo

This is a local, browser-based product demo for the restaurant operations MVP. Open `index.html` in a browser. It does not need an account or installation.

## What is interactive

- Camera-first service overview with a synthetic overhead-style scene inspired by the supplied reference: six illustrative table zones, status outlines, rough sample guest estimates and dwell timers that advance from the demo table state, plus an occupancy summary derived from the mapped demo tables. The overlay follows demo table changes and is explicitly labeled as simulated; no video feed or live camera inference is connected. Accepting a sample camera suggestion updates the sample floor and assigns a task to the least-loaded sample staff member from the four-person demo roster, with ties alternated; no staff notification is sent. Each signal and its resulting task identify whether it is a seeded demo event or a simulated walkthrough event. Sample camera events show `Not evaluated · no model`; they do not display fabricated detector confidence. A pending suggestion expires if its table state changes first, so accepting an old sample event cannot overwrite a newer state or create a task for it. Dismiss it without changing the floor. The camera setup panel can save non-sensitive recorder make/model and firmware, optional separate camera make/model and firmware, protocol notes, and illustrative zone-to-table mappings in this browser, but does not connect a device or calibrate a real image.
- Local video review and manual table-state labeling. Choose an authorized video stored on this device, replace the default sample table IDs with the IDs used in the recording, mark occupied/reset/ready/check states at playback timestamps, and export only the labels as CSV. Exports use a reviewer-provided clip label rather than the source filename; detector reports use a generic prediction-file label. The video is not uploaded or saved by the demo, and no AI detection or waiter notification runs in this screen.
- Optional local comparison of a separate detector CSV with the manual labels over an explicitly selected, fully reviewed video segment. Predictions and labels outside the segment are excluded, and false alerts per video-hour use only its duration. It reports event-level overall and per-state precision/recall, false alerts, and mean timing error. Export a spreadsheet-ready evaluation summary without including the video or prediction rows. It expects already-converted table-state predictions; it does not run a detector or evaluate Roboflow image classes directly.
- Floor tabs and table detail panel; normal table actions follow the service sequence (ready → occupied → check/reset → ready). Managers can add a table to Main Dining, Patio, or Bar with a unique ID and seat count; it appears in the sample grid and camera-zone mapping list. An expandable correction control records deliberate manual state corrections in this browser's demo activity.
- Staff task creation, assignment, progress, completion, and manager confirmation, with a recent activity feed. Starting a table-reset task marks an occupied/check table as Resetting; manager confirmation marks it Ready only if that same reset state has not changed, completing the sample turnover. Camera-accepted sample tasks retain and display their originating event ID for traceability.
- Management analytics with current table-state and task counts that respond to demo actions, plus completed turnovers, seated-service duration, and reset duration calculated only from completed occupied → reset → ready cycles; historical charts and benchmarks remain clearly labeled sample data. CSV summary and table-state history exports are explicitly sample-only and stay on the local device.
- Supporting inventory outlook: edit on-hand stock, expected daily portions, order timing, a default lead time, and per-ingredient supplier lead times. Per-serving structured recipes belong to menu items and feed this estimate. Unavailable menu items are excluded from expected demand. Blank stock, demand, recipe, or lead-time inputs remain unknown rather than silently becoming zero. The estimate calculates ingredient consumption and days of stock remaining; it flags runway at or below the estimated delivery time as at risk, including an exact-boundary match. Export a local CSV with the quantities, assumptions, unknowns, and delivery-risk outlook; it does not create an order.
- Menu & guest view: manager demo role can add/edit customer-facing dishes, choose menu currency, import/export CSV, and mark a dish available/unavailable. A same-device guest preview shows dish descriptions, ingredient/allergen notes, prices, and availability. A CSV template is downloadable in the menu screen and included as `menu-template.csv`; CSV imports are size/type-limited to 1 MB and 100 dishes, and spreadsheet formula prefixes are neutralized on export. Imported dishes need expected portions and reviewed structured recipes before affecting inventory. This is not yet a hosted customer QR menu; menu changes stay in browser storage and cannot sync to customers on other devices.
- Manager/server view switch for demoing role-specific presentation. The server view can select a sample staff identity, sees only that person's task queue, can create a task assigned to that person, and can start or complete assigned tasks. Managers can reassign open or active tasks and confirm completion. This is a presentation flow, not server-enforced authorization.
- A collapsed, mandatory security release checklist on the overview.
- Reset sample shift restores the seeded table states, tasks, camera suggestions, and shift activity. Manager-added tables remain in their floor area and return to Ready. Camera notes/mappings, menu edits and currency, and inventory assumptions are retained.

## Quick demo walkthrough

For the real-camera path, use the [camera/NVR identification guide](CAMERA_INFO_GUIDE.md) and record device-by-device qualification evidence in the [camera compatibility matrix](CAMERA_COMPATIBILITY_MATRIX.md). RTSP or ONVIF being listed is only a starting point; it does not prove a stream is usable or reliable at the restaurant.

1. On Overview, accept **EV-01 for T13**. T13 is mapped in the illustrative camera overlay, so its sample state should change from **Check requested** to **Resetting**, the occupancy estimate should recalculate, and a task should be assigned to the less-loaded sample server. No real staff notification is sent. Dismiss the suggestion instead to leave the floor state unchanged.
2. Use **Simulate sample signal** to create a synthetic occupancy, dwell-check, or table-clear suggestion for an eligible table, then accept or dismiss it. This is a repeatable walkthrough aid; it does not inspect a camera or run AI.
3. On the floor plan, select an occupied table such as T01, choose **Start reset**, then **Mark ready**. This records a full sample service/reset cycle for the turnover and timing measures. Open **Recent table history** in the table details to inspect the state changes, demo actor, timestamps, source, and any linked sample camera event ID.
4. For a complete reset loop, create a **Reset table** task for an occupied/check table. Switch to the assigned server, use **Start** (the table becomes Resetting), then **Mark done**; switch back to manager and **Confirm** (the unchanged reset becomes Ready and counts as a completed turnover). If the table state changed meanwhile, confirmation leaves its floor state untouched.
5. In Menu & availability, add/edit a dish or import the menu CSV template, then mark a dish unavailable and open Preview guest menu to see the customer view update. Expand Inventory estimate setup to map expected portions and stock ingredients per serving.
6. In Inventory outlook, edit sample stock, menu assumptions, or an ingredient's lead time to see the estimated daily consumption, runway, and delivery risk change. Blank values are treated as unknown; enter zero only when zero is known.
7. In Video review, choose a locally stored, authorized clip, seek to a table-state change, select the table and state, then mark the playback time. Export the manual labels as CSV; the video itself is not included. If you later have a separate table-event prediction CSV, load it in the comparison panel to see simple local metrics.

Every action above changes browser-local sample data only. It does not connect to restaurant equipment or send staff notifications.

## Extending inventory assumptions

The Inventory outlook screen can add restaurant-specific ingredients to the local estimate. Choose a stock unit (`ea`, `g`, `kg`, `ml`, or `L`), then enter stock, supplier lead time, expected portions, and per-serving recipe quantities. Recipe quantities convert between grams and kilograms or between millilitres and litres; incompatible types stay separate. New ingredients begin with unknown stock and remain in the demo after resetting sample stock. Remove a custom ingredient only after unlinking it from every dish recipe. The prototype does not model yields or waste, or verify stock counts.

## Important boundaries

- The camera panel is illustrative. No camera, video, or computer-vision model is connected.
- The Video review screen only plays a user-selected local video (up to 16 GiB) and records manual labels in the open page. It does not create a trained dataset by itself, and labels are lost when the page is closed unless exported. Playback depends on browser codec support. Use only authorized footage; exported labels do not include the video.
- Detector CSV comparison is a lightweight local evaluation aid, not a validated benchmark or deployment gate. It expects table ID, state, and clip-relative seconds from a separate detector/tracking pipeline. Use held-out recordings and restaurant-approved limits before using any model operationally.
- Table events, staff, tasks, menu recipes, sales volume, and stock are sample inputs stored in local browser storage. They are not shared across users or restaurants.
- The role switch is a presentation aid, not authentication or access control. There is no backend, live notification delivery, POS connection, hosted guest QR menu, or supplier purchase-order connection. Guest menu preview runs on this device only; publish a public menu URL backed by shared restaurant data before creating real customer QR codes.
- Inventory calculations are rough estimates: daily ingredient use is the sum of expected portions multiplied by recipe quantities. They do not currently account for waste, yield loss, staff meals, reservations, changing sales mix, or stock-count error.
- Role permissions, restaurant-level data isolation, security verification tests, and the consolidated security checklist remain mandatory before release. The exact checklist supplied by the user is recorded in `REAL_WORLD_BUILD_PLAN.md` and visible in the dashboard's release-gate details. The local prototype escapes browser-stored task, event, table, menu, and ingredient text before rendering and builds camera table-mapping controls with DOM text nodes, but this is only a prototype safeguard; it does not replace server-side validation, authorization, or the required security verification.

## Inputs needed for a real pilot

1. Camera/NVR manufacturer and model, supported stream protocol (such as RTSP/ONVIF), camera count, and camera placement/floor plan. The user has IP cameras or an NVR; the exact model and protocol are still needed. Do not share passwords or stream credentials in chat.
2. A first pilot restaurant's floor plan, table identifiers, and staff roles. A pilot location is not selected yet.
3. Menu items, recipe quantities and units, expected daily order mix, current stock counts, and supplier lead times. These details are not ready yet. The manager CSV template can help collect customer-facing menu details; prices are imported in the currently selected currency; a separate structured recipe mapping is needed for inventory estimates.
4. No screenshot is needed to recover the checklist: the user supplied its text, and it is now recorded in `REAL_WORLD_BUILD_PLAN.md`.

The next engineering phase is a shared, authenticated backend with restaurant-scoped data, manager menu publishing, and a public guest menu page; then connect a camera integration selected for the pilot hardware. Inventory can then be calibrated with structured recipes, POS sales, and actual receiving/stock-count data. A showcase handoff should include per-page screenshots and a clean GitHub repository after the UI and release checklist are reviewed; decide repository visibility before publishing. See `SHOWCASE_RELEASE_GUIDE.md` for the image list and publishing checklist.
